# SubStore 自主管理客户端节点池与国旗分组设计

## 目标

将“某个客户端是否支持某个协议”的选择权从仓库代码移到用户自己的 SubStore。仓库不再根据客户端协议白名单自动丢弃节点，而是读取用户为每个客户端准备的组合订阅，完成通用节点归纳、名称规范化、国旗/洲别排序、协议类型标注和客户端配置格式渲染。

这次改造解决三个长期维护问题：

1. 客户端新增协议时，不会因为共享协议注册表没有及时更新而被静默过滤。
2. 用户可以在 SubStore 中分别决定 Egern、Anywhere、Shadowrocket、Surge、sing-box 和 OneXray 使用哪些来源、协议和节点。
3. 六个客户端继续共享一套节点命名和分组逻辑，同时保留各自配置格式、路由和策略组的差异。

节点通常已经带有国旗，因此国旗是首选的地域依据。没有国旗时才根据节点名称推断；仍无法识别的节点进入 `🌐 其他`，并记录不含私密值的诊断计数。

## 非目标

- 不把真实节点、SubStore API、凭据、服务器、端口或私密输出 URL 写入仓库。
- 不让仓库动态访问用户的 SubStore 管理 API。
- 不尝试让六个客户端共享同一种原生节点格式。
- 不保证“客户端原生新增协议”在本仓库的所有渲染器中无需任何代码适配。取消自动过滤解决的是误删问题；如果某个渲染器完全不知道新协议的目标格式，仍必须明确报错或后续增加适配。
- 不把所有未知字段静默复制到客户端输出。安全字段和客户端格式字段仍需经过对应渲染器的明确处理。

## 当前基础与问题

仓库已经有以下可复用基础：

- `shared/nodes/normalize-nodes.js` 已经执行节点去重、名称清理、国旗/洲别识别和稳定排序。
- `shared/nodes/regions.js` 已经支持从节点名称识别常见国家和地区。
- `shared/policies/filters.js` 与 `shared/policies/catalog.js` 已经定义 `🌏 亚太`、`🌍 欧洲`、`🌎 美洲` 和 `🌐 其他/未分类` 的顺序及洲级策略组。
- 六个客户端已经有自己的节点格式渲染器和 Profile/Config 策略组渲染器。

现有问题是客户端渲染链在归一化后调用 `filterNodesForClient()`，共享能力表同时承担协议注册、客户端白名单、字段兼容检查和诊断。结果是：SubStore 已经提供的节点可能在进入目标渲染器前被排除；尤其是客户端已经支持、但仓库白名单或字段模型尚未更新的协议。

## 方案比较

### 方案 A：六个客户端组合订阅 + 仓库取消客户端协议过滤（采用）

在 SubStore 中维护一个总组合和六个客户端专用组合。每个客户端组合由用户自己使用 SubStore 的来源、类型过滤或脚本筛选维护。仓库只处理对应组合中已经被用户选出的节点。

优点：维护边界清楚、保留现有项目的统一命名和策略组、不会因为共享白名单过期而误删节点。缺点是新增协议如果没有对应客户端格式渲染器，仍会明确失败。

### 方案 B：一个能力 JSON + 仓库按 JSON 过滤

把客户端协议允许列表放在 SubStore File 或远程 JSON 中，由脚本读取。优点是只有一个维护文件；缺点是仍然由仓库解释客户端能力，字段语义容易和真实客户端脱节，且用户无法直观看到每个客户端最终使用的节点集合。

### 方案 C：节点层完全交给 SubStore 原生目标转换

仓库只输出通用节点目录，SubStore 负责转换为六种客户端格式。优点是协议支持可以跟随 SubStore；缺点是会削弱现有项目的统一路由、策略组、诊断和平台 Profile 能力。它可以作为以后“完全免代码协议升级”的独立方向，不纳入本次改造。

## 采用的架构

```text
SubStore 原始来源
        │
        ▼
apple-proxy-all                         总节点池
        │
        ├── apple-proxy-egern            用户维护的 Egern 节点集合
        ├── apple-proxy-anywhere         用户维护的 Anywhere 节点集合
        ├── apple-proxy-shadowrocket      用户维护的 Shadowrocket 节点集合
        ├── apple-proxy-surge             用户维护的 Surge 节点集合
        ├── apple-proxy-singbox           用户维护的 sing-box 节点集合
        └── apple-proxy-onexray           用户维护的 OneXray 节点集合
                │
                ▼
        对应客户端 SubStore 脚本
                │
                ├── 通用归一化：去重、国旗、洲别、协议类型、排序
                ├── 对应客户端格式渲染
                └── 对应客户端策略组和路由 Profile
```

### SubStore 维护边界

保留一个包含全部来源的总组合，例如 `apple-proxy-all`。在其基础上创建六个客户端组合。六个组合可以复用相同的原始来源，但由用户分别配置类型过滤、正则筛选、脚本筛选和节点操作。

每个客户端的 File/Script Operator 任务指向对应的客户端组合，而不是统一读取总组合。这样用户可以：

- 让 Shadowrocket 组合包含 AnyTLS；
- 让 Egern 组合只包含已经验证过的 AnyTLS 字段形状；
- 让 Surge 组合暂时排除某个协议；
- 在某个客户端支持新协议后，只修改该客户端 SubStore 组合。

仓库文档将提供组合命名建议和任务映射，但不保存用户真实组合内容。SubStore 脚本可以通过 `produceArtifact({ type: "collection", name: "...", platform: "JSON", produceType: "internal" })` 获取用户已经选择的节点数组；组合名作为任务参数传入，不在代码中硬编码。

### 项目能力边界

项目将协议处理拆成三层：

1. **通用节点验证**：检查对象、节点名、服务器、端口和必要认证字段，防止空节点、伪节点和明显损坏的输入进入输出。
2. **通用归一化**：不按客户端协议白名单过滤；保留节点类型和字段，完成去重、名称、国旗、洲别、来源和稳定排序。
3. **客户端格式渲染**：将已选节点转换为 Egern YAML、Anywhere Clash YAML、Shadowrocket/Surge 格式、sing-box JSON 或 OneXray JSON，并生成各自的策略组。

`protocol-registry.js` 可以继续提供协议规范化、显示名和通用必填字段元数据，但不再作为客户端支持矩阵。客户端渲染器不得在归一化阶段调用 `filterNodesForClient()` 来静默删除用户已经选入该客户端组合的节点。

如果节点类型没有对应渲染分支，输出任务必须报出客户端、协议类型和“需要在 SubStore 组合中移除或等待适配”的可操作错误；不得生成缺失节点的成功输出，也不得把安全字段静默丢弃。

## 节点归纳与命名

### 国旗优先

`classifyRegion()` 的优先级调整为：

1. 节点名中已有的一个国旗；
2. 节点名中的国家/城市关键词；
3. `🌐` 和 `other`。

如果国旗和文字推断冲突，保留用户提供的国旗作为输出分组依据，并增加 `flag-text-conflict` 诊断计数。多个国旗时使用第一个国旗，并保留告警计数，避免节点在不同刷新中漂移。

### 节点类型标注

规范化名称在来源和能力后缀之前增加显示类型，例如：

```text
🇯🇵 东京 · AnyTLS｜自建·U
🇩🇪 Frankfurt · VLESS｜机场
```

现有的 `｜自建`、`｜机场`、`·U`、`·链` 和 `🔗` 机器可读后缀必须保持可匹配，不能因为插入协议标签破坏已有来源、UDP、链式代理过滤器。

已知协议使用规范显示名；未知协议使用其规范化后的原始类型字符串，避免未知类型在归纳阶段变成空标签。

### 稳定排序

节点排序固定为：

1. `🌏 亚太`；
2. `🌍 欧洲`；
3. `🌎 美洲`；
4. `🌐 其他/未分类`；
5. 国旗；
6. 协议显示名；
7. 节点显示名；
8. 稳定内部身份。

继续使用现有“亚太”名称，以覆盖澳大利亚、大洋洲和亚洲地区，避免改变当前规则和客户端策略组的既有语义。

## 策略组设计

Egern、Shadowrocket、Surge、sing-box 和 OneXray 的 Profile/Config 都保留名称为 `🚀 节点选择` 的主入口，以避免现有规则引用失效。主入口下生成洲级组，洲级组下生成按国旗聚合的节点组，节点组最终包含具体节点。Anywhere 的远程节点订阅只输出 `proxies` 节点列表，不伪造远程策略组；Anywhere 的策略组和规则绑定继续在 App 本地维护，节点名称仍携带国旗和协议类型。

```text
🚀 节点选择
├─ 🌏 亚太
│  ├─ 🇯🇵 日本
│  ├─ 🇸🇬 新加坡
│  └─ 🇦🇺 澳大利亚
├─ 🌍 欧洲
│  └─ 🇩🇪 德国
├─ 🌎 美洲
│  └─ 🇺🇸 美国
└─ 🌐 其他/未分类
```

协议类型通过节点名称标注，并作为可选的类型过滤维度保留在 `_profile` 元数据中。第一版不为每个国家再生成一个协议子组，避免节点较多时产生过深、过大的策略组树；如果实际使用中需要，可以在后续增加 `typeGroups=on` 的显式选项。

各客户端继续使用现有的策略组适配器：

- Egern：生成 `policy_groups`，保留现有 QUIC、自动测速、故障转移和节点订阅边界。
- Shadowrocket：生成 `[Proxy Group]`，保留订阅动态组和现有规则引用。
- Surge：生成 `[Proxy Group]`，保留远程节点池和 `policy-regex-filter` 机制。
- sing-box：生成 selector/urltest outbounds，保留洲级层次和规则下载故障转移。
- Anywhere：节点订阅输出保持 Clash YAML；其本地规则/绑定仍由 Anywhere 维护，不把完整 Profile 假装成远程订阅。
- OneXray：按其 JSON/Profile 结构生成节点和选择器；不把 OneXray 的路由规则转换成其他客户端格式。

五个支持 Profile/策略组输出的客户端统一采用“主组 → 洲组 → 国旗组 → 节点”的结构。Anywhere 使用“节点列表 + 国旗/协议名称”结构，由用户在 App 内把节点加入本地策略组；输出必须保持确定性并通过该客户端订阅校验器。

## 参数和任务变更

各客户端节点任务新增或统一一个安全的组合名参数。参数只允许引用 SubStore 中的组合名称，不允许在脚本参数中传入原始订阅 URL 或节点内容。

建议参数语义：

```text
output=nodes
type=collection
name=apple-proxy-egern
clientChain=off
```

Profile 任务使用同一客户端对应的节点订阅 URL 或组合名，保持现有私密 URL 不进入仓库。Anywhere 当前对固定组合名的限制需要改为安全校验后的可配置组合名；其余客户端已有的 `name` 参数也要统一检查组合名边界。

文档将把旧的统一组合 `apple-proxy-sources` 标记为兼容迁移入口，而不强制用户一次性删除。迁移完成前，旧任务和新任务可以并存，用预览结果确认新组合非空后再切换客户端 URL。

## 失败处理与隐私

- SubStore 组合为空：任务失败，不发布空节点订阅。
- 节点基础字段损坏：按通用验证原因计数，不输出节点值。
- 未实现的客户端渲染类型：任务失败并显示客户端和协议类型，不把节点静默排除。
- 国旗缺失或冲突：使用确定性回退并记录聚合告警。
- 重复节点：按现有身份规则去重，保留确定性候选。
- 诊断只包含总数、接受数、排除原因、协议计数、洲别计数和告警计数，不包含节点名、服务器、密码、UUID、PSK、私钥或原始订阅 URL。
- 所有新参数都进行普通对象、字符串、长度、控制字符和组合名边界校验，防止 SubStore 脚本上下文和输出内容被注入。

## 实施顺序

1. 增加通用归纳元数据：协议显示标签、国旗分组键、洲别、类型和排序字段。
2. 将六个客户端任务的组合名改为参数化，并移除客户端协议白名单造成的静默过滤。
3. 为每个客户端增加“未实现协议显式失败”的渲染边界和聚合诊断。
4. 扩展共享策略组模型，增加国旗节点组，保持现有主组、洲组、服务组和规则引用。
5. 更新各客户端适配器、校验器和脱敏 fixtures。
6. 更新 SubStore 总指南和六个客户端维护文档，加入六个组合的命名、筛选、预览、切换和回滚步骤。
7. 构建 bundle，刷新脱敏示例，运行全量测试、秘密扫描、任务检查和客户端结构校验。
8. 在用户 SubStore 中创建六个客户端组合并逐项刷新；保留旧任务用于回滚。

## 测试设计

### 共享节点测试

- 有国旗的节点始终按国旗分组，即使城市关键词冲突。
- 无国旗但可推断的节点获得稳定国旗。
- 完全未知地区进入 `🌐`，且诊断不泄露节点值。
- 已知和未知协议都能完成通用归一化；未知协议不被客户端白名单静默删除。
- 类型标签插入后，来源、UDP、链式代理和节点身份过滤仍保持原有语义。
- 节点排序输入顺序无关，重复刷新结果确定。

### 客户端测试

- 六个客户端均从各自组合名读取节点。
- 用户选入的已实现协议会进入对应输出。
- 用户选入的未实现协议会失败并显示聚合原因，而不是成功生成缺节点输出。
- Egern、Shadowrocket、Surge、sing-box 和 OneXray 都存在 `🚀 节点选择`，洲组和国旗组引用存在且无环；Anywhere 输出合法节点列表并保留国旗/协议名称。
- Egern、Shadowrocket、Surge、sing-box、Anywhere 和 OneXray 的现有规则、Profile 根结构和私密节点边界不回归。
- bundle 运行结果与源码入口一致，生成物和脱敏示例不手工修改。

### 文档与发布测试

- 文档不含真实 SubStore API、订阅 URL、服务器或凭据。
- 六个组合名、脚本参数和任务依赖在文档中保持一致。
- `npm test`、`npm run verify`、`npm run check:secrets`、`npm run check:actions` 和客户端 workspace verify 通过。
- 不把 `dist/`、`public/` 或用户私密输出当作源码编辑。

## 验收标准

1. 用户可以只在 SubStore 中调整六个客户端组合的协议和节点选择，不需要修改共享能力 JSON。
2. 同一个 AnyTLS 节点不会因为仓库客户端白名单过期而被静默排除。
3. 具有国旗的节点按国旗进入正确洲级和国旗级策略组；无国旗节点有稳定回退。
4. 节点显示名包含可读协议类型，同时不破坏现有来源、UDP 和链式代理后缀。
5. 六个客户端都使用自己的组合输入；五个配置型客户端生成各自的 `🚀 节点选择` 主组，Anywhere 生成可供本地策略组选择的国旗/协议标注节点列表。
6. 不支持的渲染类型会明确失败，不会伪造、静默丢弃或泄露私密诊断。
7. 旧的统一组合和任务可以在迁移期间保留并回滚。
